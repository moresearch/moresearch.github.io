Harness Patterns for Agentic AI Systems

A catalog of thirteen harness patterns for agentic AI systems, distilled from this blog's own archive — the append-only session log, the loop as a config row, policy waterfalls with monotonic guards, capability seams, the agentic-first interface, durable execution and state governance, the sandbox stack, the verifier layer, the harness as measurement instrument, tasks that fight back, per-agent scope and identity, the bill as assertion, and the harness that builds the harness. Each pattern is subtitled, traced to the posts where it appears with the evidence each post carries, and weighed: what it buys, what it costs, and where its guarantee stops.

A harness is the environment an agent lives in: everything between the model and the world. It decides what the agent can see, what it can do, and how the outcome is judged. This blog has been arguing for months that the harness — not the model — is where the leverage concentrates. The numbers have arrived to back it: the same model finished between 47% and 67% of real tasks across eight different harnesses while cost per finished task varied sevenfold, and the same weights score 3.4 points apart on the public Terminal-Bench board under two major harnesses. Nothing about the intelligence changed. The wrapper changed.

This post is a synthesis of the posts that came before it. Across the archive — the DeepSeek Harness teardown, the spatiotemporal composability paper, the Sonar AC/DC analysis, the harness-engineering series, the durable daemons series, the token-economics reading, the sandboxing and agentic-CLI posts — the same design decisions keep recurring, each time with evidence attached and each time with a price. Together they form a catalog of harness patterns: recurring solutions to recurring problems in agent runtime design, each one a choice with an alternative that lost and a cost that has to be paid.

The catalog is organized into four families. Memory and state patterns decide how the agent's past is stored, replayed, and billed. Composition and interface patterns decide what the harness is made of and what the agent sees. Policy and safety patterns decide what the agent may not do. Learning and verification patterns decide how the agent gets better.

Pattern 1 — The Append-Only Log: history is the boundary

The spine of the DeepSeek Harness design is the session log: an append-only log of typed events from which the model's message history is derived by a pure fold, never stored. Every message-producing append must carry a surfaceOp marker and sourceEventSeqs; the surface manager throws on a raw event without a marker, on a replacement that changes anything but content, on a non-contiguous sequence number. The derived messages are deep-frozen — mutating logged history through a projection is unrepresentable, because it throws. The rule is stated bluntly in the repository: "Once something has been sent to the model, you do not go back and change it. A wrong file path sitting in the history, you leave it there and append a new line saying it was wrong." As I documented in the DeepSeek Harness teardown, this is not bookkeeping. It is a billing design, a correctness design, and an audit design at once.

The insight the pattern rests on: history is not a record of the agent; it is the boundary of what the agent can do. A harness that edits history gives the model a world where the past is negotiable. An append-only log gives it a world where the only move is to append. The always-on agents survey reaches the same place from the other side — its diagnostic axes include mutability (append-only, versioned, or freely overwritable) and provenance (reconstructing exactly what state the agent had at decision time), and its lifecycle model lists audit and rollback as stages most current systems simply lack. A log that cannot be rewritten is the prerequisite for all three.

The pattern's power is visible in the economics. Providers price cached input tokens at a fraction of uncached ones — on DeepSeek's own price list, roughly a third of a cent per million tokens cached against 43.5 cents uncached, about 120x — and the condition for the discount is that the leading tokens of this request are word-for-word identical to the last one. The Every Token Has a Price Tag post framed the larger shape: the unit got cheaper but the task did not (an autocomplete action eats a few hundred tokens; an agentic task eats millions), and the shape of the bill is a design decision. The append-only log is how a harness keeps most of its traffic in the cached column — the same week the harness went free, DeepSeek's pricing page introduced peak/off-peak billing that tripled the uncached input price.

The tradeoff. The past cannot be fixed, only annotated — so every mistake costs extra tokens in corrections. Context windows are finite, so the harness must compact, and compaction is the pattern's hardest problem: the first summarizer sent a fresh system prompt at the front of the request, invalidating the entire prefix; the fix moved the directive to the end so the summary call is a genuine prefix-extension of the warm request. The discipline constrains the prompt itself: no timestamps, no volatile data in the prefix, tool descriptions sorted in one fixed order — the clock that most harnesses write into the prompt top is exactly what throws the cache bookmark away. And immutability collides with governance: the always-on agents survey notes that forgetting — deleting from backups, cached contexts, and fine-tuned weights — is the least-solved stage of the state lifecycle, and an append-only log makes it structurally harder, not easier. Finally, the log is only as durable as its format: DeepSeek's SESSION_FORMAT_VERSION sits at 0 with no compatibility promise, so the pattern's guarantee is process-internal today.

Pattern 2 — Durable Execution and State Governance

An always-on agent is a persistent-state system; the persistence is the feature. The durable daemons series specifies the pattern as four conditions — persistence, stateful memory, autonomous action, and crash-proof execution — forming the hierarchy Agent ⊃ Daemon ⊃ Durable Daemon. Condition 4 is the one that separates a daemon from a durable daemon: workflows survive process death, machine reboot, and database failover; completed steps never re-execute; in-flight steps resume from the last checkpoint; and the audit trail comes along as a byproduct. The execution post makes the stakes concrete with the trading daemon: checkpoint before placing the order, checkpoint the confirmation after; on recovery, replay and resume. "A duplicate order loses capital. A duplicate email is embarrassing. The difference is condition 4."

Two production implementations anchor the pattern: Temporal (2019), a centralized orchestration server at DoorDash/Snap/Stripe/Uber scale, and DBOS (2023), Mike Stonebraker's library that turns a Postgres write into the checkpoint with 1–2 ms step latency. The implementation is composable through choreography: daemons coordinate by writing shared state and observing each other's outputs — no orchestrator, no message bus, just a database and independent triggers. The DeepSeek teardown demonstrates the same principle inside one runtime: because the model's context is recomputed from the log before every request, a crash at step 80 can be replayed and continued from the same log and the same context, as if nothing happened.

The tradeoff. Durable execution guarantees exactly-once within its control boundary — external side effects still require idempotency keys, because an order can fire twice on recovery and only the exchange can deduplicate. The database becomes a single point of the architecture, and checkpointing adds latency to every step. And the harder half of the pattern is governance, not durability: the always-on agents survey coded 435 papers and found the literature "heavily skewed toward accumulating and retrieving state" while validation, forgetting, auditing, and rollback are barely covered — "we are building agents that accumulate state aggressively and have almost no machinery for unwinding it." Its AOEP-v0 protocol is the first attempt to evaluate agents on state recovery obligations ("if we corrupt a piece of the agent's state, does it detect the corruption? can it recover?") rather than answer quality. That is the right test for the pattern, and almost nobody passes it yet.

Pattern 3 — The Bill as Assertion

The DeepSeek loop composes every request the same way: the header folds from the log, the agent/request waterfall may propose the config, and the final GenerateOptions is deep-frozen and marked so an invariant checker can recognize conversation work. The invariant module — a separate companion plugin — replays the log in a fresh session on every request and compares its derivation against what the loop is about to send, because "the live cache cannot vouch for itself." The rejected alternative is the telling part: detect-and-report was refused because "a warning arrives after the bad request has already shipped." On top sits a paid test run against the real API that fails unless the second request in a conversation reports cached input tokens. The bill is the assertion. Cold cache, red test.

This is the harness pattern that turns the token economics post into an architecture requirement. The Jevons paradox is in full effect — prices down 98% since late 2022, consumption up ~150x, bills still tripled — because the unit that got cheap is not the unit of work: an agentic task consumes millions of tokens where autocomplete consumed hundreds, and even at 2026 prices a task costs roughly 200x the interaction it replaced. Inside the firm, an uncapped AI resource is a tragedy of the commons: rivalrous in consumption, free at the point of use, with the bill going to the division. Microsoft's response — token budgets, dashboards, cheaper defaults — is the standard answer to the standard problem, and the asymmetry behind it is that spend is measurable while productivity is not: "any technology that generates measurable cost and unmeasurable benefit will, in the absence of a productivity measurement, be governed by its cost." The harness pattern inverts this: if the cost side cannot be trusted to report itself, the harness should assert it — make the cache hit a CI gate, make the bill a test.

The tradeoff. Prefix-cache discipline is a constraint on prompt design that conflicts with legitimate volatility: session-relative timestamps, randomized ordering, and dynamic system prompts all become liabilities. The invariant checker costs a full log replay on every request — it is the most expensive self-check in the design, and it exists precisely because the cheaper alternative (comparing consecutive requests) ships the bad request first. The paid test run costs real money by design, which is the point and the objection. And the pattern is hostage to the provider's pricing: peak/off-peak billing means the value of the cached column changes hour to hour, and a harness that keeps the prefix warm is only as good as the price list it is warm against. The shape of the bill is a design decision — but the provider can change the shape faster than the harness can.

Pattern 4 — The Loop Is a Row: composition over configuration

A running DeepSeek harness is a plugin tree composed at boot from ordered layers: a profile is a named composition, a bundle is a distribution format, a patch targets a row by id and replaces its whole config. dump-config prints the tree your machine actually boots, and the claim is total — "any row it prints can be replaced by a patch of your own." The agent loop itself is a row: @deepseek-ai/dsh-agent-loop is "the only concrete loop plugin and is itself swappable — nothing outside it may depend on it," and disabled: true on the loop's config rule means there is no agent. The main loop and a tiny badge plugin are equals in the eyes of the config.

The theory underneath is spatiotemporal composability, the 88-page calculus from Peking University and DeepSeek-AI: temporal composability (removing a component undoes everything it did) and spatial composability (when the world changes, dependents reconnect or wait, never crash), built from revertible effects and reactive coeffects through a single unified context. The paper's evidence that this is a real gap: 87 of the top 100 VS Code extensions require a host restart to remove, and "Reload Window" exists because nobody had a vocabulary for what was missing. The calculus makes teardown derived rather than written — the author supplies one line per atomic operation and the runtime composes the inverses in reverse order — which is the only cleanup an autonomous agent will reliably perform: "guarantees you must remember are guarantees an agent will, at some point, not." Cordis, the implementation, has 4,000+ Koishi plugins as its evidence base.

The tradeoff. Composition is paid for in incident reports. Twice, a quiet configuration mistake silently broke the DeepSeek product; once, 178 green tests and a full coverage set sat on top of a system that died the moment a real editor connected. Their answer was pre-release checks — there are 27 of them now, and each one is the pattern's bill: "pay it one crash at a time." The structural guarantee is also narrower than it sounds: revertible effects guarantee the teardown you supplied is executed, in order — not that it is correct. If an effect's inverse is wrong, the recovery is wrong, and no amount of structure detects it. And recovery is up to observational equivalence, not literal restoration — what you expose as dependencies is what recovery promises to restore, which is why the system boundary is the deepest design pressure in the paper.

Pattern 5 — Capability Seams: definition, provider, consumer

A swappable capability has three roles that change at different rates: a Service Definition owning the ctx.<key> and the vocabulary, one or more Service Providers implementing it, and a Consumer (usually a model-facing tool) programming against it. The seam note records why: "swapping a local executor for a sandboxed one would churn the tool schemas the model sees, even though the model-facing contract never changed." The rule is to split only when roles evolve independently — packages/shell is the reference template, and the subagent seam shows the payoff: providers registered by name include in-process spawn, fork, ACP, Codex, Claude Code, and the harness's own SDK, all behind one interface, with a provider advertising its start-time capabilities statically so a request needing one it lacks is rejected before any run exists.

The industry's attempt to standardize the tool seam is MCP, and the pattern's stance on it is precise: MCP is one consumer family, not the seam itself; the seam is the three roles behind a stable context key. The most striking move is mounting rival harnesses as providers rather than reimplementing them — the Claude Code backend calls Anthropic's own agent kit at a pinned version and hands it the real binary's path; the Codex backend starts OpenAI's own app server over stdio. The agentic-first CLI post supplies the same discipline at the interface layer: the contract is the architecture — --json on every state-producing command, stable documented schema, versioned and additive.

The tradeoff. Three roles mean three surfaces to keep in sync, and the drift is the failure mode — which is why the DeepSeek pattern is paired with a type-graph analyzer (Typert) that generates the RPC contracts, tool catalogs, and API docs from one source with freshness gates that fail the build on drift. Without that mirror, the seam pattern decays into documentation rot. There is also the question of whether a capability is worth a seam at all: splitting prematurely buys indirection with no payoff, and the rule "split only when roles evolve independently" is easy to state and hard to apply. And every seam is an integration boundary — zero overhead is zero attack surface: "every integration is a boundary where a substitution can hide," and a seam that mounts rival vendors' binaries is a seam that inherits their supply chains.

Pattern 6 — The Interface Is the Product: ACI discipline

The founding claim is SWE-agent's: agents are "a new category of end users with their own needs and abilities," and they need specially-built interfaces to the software they use. The result that made the claim famous — a custom agent-computer interface achieved 12.5% pass@1 on SWE-bench and 87.7% on HumanEvalFix with the same GPT-4 model — established that the interface is a performance variable, not cosmetics. The agentic-first CLI post translates this into a design discipline for the interface you already ship: structured output as the observation channel (git's status --porcelain from 2009 is the reference), determinism as trust (an agent that cannot satisfice a nondeterministic tool must verify, and verification is the most expensive thing an agent does), help text as the documentation the agent reads, exit codes and stderr as the contract, consistency as learnability, and quiet-by-default as the token budget. The benchmarks set the stakes: Terminal-Bench 2.0 found frontier agents score under 65% on hard terminal tasks, and its error analysis blames the interfaces — ambiguous output, interactive prompts, hidden state.

The pattern has a second, more radical form. Code mode in the DeepSeek harness replaces the tool list — the JSON-schema presentation — with a generated TypeScript SDK plus one run_code transport: the model writes a program that loops, branches, and batches reads, and only what it prints or returns comes back into the conversation. The reasoning is borrowed from Cloudflare: "LLMs are better at writing code than at emitting tool calls, because they have seen millions of lines of real code and comparatively few contrived tool-calling traces." The tool list is a presentation, not the interface; the program is the interface. The OpenWorker outcome layer is the same pattern one level up: the interface shifts from chat to deliverables — the agent produces a finished document, a sent message, a resolved calendar, with approval gates before consequential actions.

The tradeoff. ACI discipline is a maintenance contract: every interface change is a behavioral change in every agent that reads it, which is why the CLI post demands a versioned, additive contract and honest --help ("a lie in help text is the most expensive bug an agentic CLI can have"). The purpose-built-interface route (SWE-agent's custom ACI, MCP servers, function schemas) avoids reusing a bad interface but adds a layer to write, document, and keep in sync — the economics argument for the CLI over the protocol. Agent-optimal design can hurt human users if the interface is not designed for both. And code mode's trust posture is explicit: run_code is "bash-equivalent by design," executed in a worker thread with caps and hard termination — containment, not a security boundary, with authority comparable to the bash tool. The interface is the product, and the product is not a wall.

Pattern 7 — Per-Agent Scope and Portable Identity

The scope primitive makes one fact drive two consequences: a registration made through an agent's agent.ctx is visible only to that agent and owned by that agent's lifetime. Scoped registrations shadow global ones — the per-agent persona and per-agent tool-variant mechanism — and scope-filtered dispatch routes events about one agent's activity to that agent's listeners. This is what makes the "one row" claim of Pattern 4 honest: the row can be scoped to a single agent, and the four presets (standard, code, minimal, creation) work as per-session compositions instead of global profiles. The comparison sharpens it: VS Code scopes contributions to extensions, not per-instance; OpenHands sessions are per-conversation but capability sets are largely global; LangGraph threads state explicitly through the graph.

The identity half of the pattern comes from the Buzz post: when an agent acts inside your infrastructure, who is it? Today the answer is usually "a service account leased from a provider's API key," and the consequences are that there is no portable answer to "which agent made this change," no basis for reputation, and vendor lock-in — the switching cost is the accumulated context that makes the agent useful. Buzz's architecture separates agent identity from model access: identity is a keypair on the Nostr protocol, generated by the participant, portable across platforms; the model is a configuration choice. "They are independent axes. Most agent platforms today conflate them." The post's test for agent infrastructure is the right one: can you answer "who did what, why, and was it correct?" six months after the fact, after rotating credentials and switching platforms? The "was it correct?" column is still empty — that is Pattern 10's job.

The tradeoff. Per-agent isolation is in direct tension with the durable-daemons choreography, whose entire mechanism is shared state: Pattern 7 gives each agent a private world; Pattern 2 coordinates agents by having them observe each other's outputs. The resolution is scope discipline — what is shared, what is scoped, and who owns the boundary — which is exactly the authority and scope axes the always-on survey says are under-built. Identity portability has its own costs: a self-sovereign keypair survives platform switches, but it also survives you — revocation, rotation, and cross-user contamination ("if an agent has learned a preference from user A, should user B's interactions be influenced by it?") are governance problems a keypair does not solve. And reputation requires stability: "you cannot build a reputation system on top of rotating API keys," but a stable identity is also a persistent target.

Pattern 8 — Waterfalls of Policy, Monotonic Guards

Every tool call in the DeepSeek harness passes through a pipeline whose ordering is the doctrine: waterfalls for extensible policy, guards for final authority. tools/pre-execute runs as a waterfall — hooks, permission, sandbox decisions; a listener that owns the decision short-circuits by returning without next(). Then monotonic guards run — they deny or abstain and can never force-allow, so owner policy that must not be reordered cannot be argued around. The approval seam is fail-closed: allowed-once is the only granting outcome; a missing, throwing, or non-conforming answerer resolves to unavailable. Then execution wraps the tool body as around-dispatch — timeouts, retries, metrics — and a definition-owned finalizeContent callback, snapshotted at call start, enforces the last content-only invariant before the frozen result. Two details carry the doctrine: a call collapsed by code mode is denied before the policy pipeline, because pre-execute listeners, approval, and guards "must never observe — or worse, approve — a call that can only fail"; and cancellation is a contract that distinguishes ABORTED_BEFORE_DISPATCH from ABORTED, so "cancellation never abandons the body."

The same ordering appears in the sandboxing literature as the defense-in-depth stack: thirteen layers, each assuming the one below it will fail — the sandbox is "the accumulated constraints that make the agent's behavior predictable even when one constraint fails." And the fail-closed posture is the zero-overhead argument inverted: jail mode confines tools to the working directory, skills declare their own allowed tools and bash permission patterns, and guardrail extensions intercept tool calls mid-flight — the boundary is expressed as policy because the agent cannot be trusted to express it as intent.

The tradeoff. The ordering guarantee is the point and the cost: policy that must not be reordered cannot be delegated, so the owner policy is a choke point that every extensible hook must route through. Fail-closed approval buys safety at the price of friction — a missing answerer means unavailable, which is a denial by default, and agents running unattended need the automation path (permission presets) to be designed as carefully as the ask path. The guarantee's scope is declared, not total: the sandbox vocabulary covers file effects only — network and process visibility are out of scope by declaration — and enforcement is reported full or partial, which is the honest version of a security claim. The local backend functionally probes confinement candidates (bwrap then Landlock, Seatbelt, Windows ACL restricted tokens), picks the first that works, and fails closed if none does — which means the pipeline's behavior depends on the kernel it runs on.

Pattern 9 — The Sandbox Stack: defense in depth, honest scope

"A container is not a sandbox. A microVM is not a sandbox. A hypervisor is not a sandbox. Each is a layer of a sandbox." Amjad Masad's Sandboxes Are Hard is the pattern statement: AI agents escape sandboxes, and the reason is that a single layer of isolation is not a security architecture. Replit's answer — built on a decade of running arbitrary untrusted code — is a stack: zero-trust service-to-service auth, seccomp-bpf-hardened containers, per-customer GCP projects, microVM migration, an append-only Git sidecar, a transparent secrets proxy, scanned MCP calls, built-in auth, forkable databases, Nix supply-chain integrity, continuous external assessment, and an internal AI red-teaming harness. The posture is the design: "assume zero-days exist — because they do. Assume your isolation will eventually fail." Compliance is not security; a clean pen test is a snapshot.

The complementary pattern is subtraction. The zero-overhead post makes the argument that the industry's response to supply-chain risk adds more of what caused it — every verifier needs its own verifier, and "verification below a certain size is theater." zot's answer is four tools, eleven dependencies, no telemetry, extensions opt-in as subprocesses: "an agent with a thousand dependencies is a thousand doors." The two patterns are not opposites: the sandbox stack constrains what a compromised agent can reach; the subtraction stack shrinks the number of things that can be compromised. And the spatiotemporal composability post contributes the boundary concept: the one-door context is a capability mediator over dependencies, not isolation of code — "the context is the door; the door is not the walls" — and recovery is promised only as far as the system boundary, which is a design decision. Composability ends where the world begins: an email sent, a payment moved.

The tradeoff. Every layer is itself an attack surface and a maintenance burden — thirteen layers is thirteen things that can be configured wrong, and the deepseek-harness lesson (config accidents break products silently) applies with compound interest. The subtraction answer to that — fewer layers — trades protection depth for verifiability, and it cannot defend against the classes of attack that need a real boundary (kernel escapes, multi-tenant isolation). There is a UX cost: fail-closed sandboxes make the agent slower and noisier, and teams respond by whitelisting until the sandbox is a formality. And the deepest honest limit is scope: file-effects-only vocabulary, bash-equivalent trust, "an opt-in development tool" — the guarantees stop where the declaration stops, and every post in this family ends by saying so.

Pattern 10 — Verifiers Are King: Guide, Verify, Solve

The Sonar AC/DC framework — Guide, Verify, Solve — is the canonical statement of the pattern, and its evidence is the productivity paradox: AI coding agents deliver an initial 3-5x velocity boost that begins to evaporate within three months, because "every line they wrote is a line nobody reviewed." Guide is preemptive verification — context, standards, and constraints the agent cannot violate because it never knew them; Sonar claims a 30% token reduction from context augmentation alone. Verify is zero-trust, multi-layered: algorithmic analysis for the deterministic problems (data flows, known CVE patterns, secrets) plus agentic analysis for the semantic ones (intent, business logic, the unknown unknowns). "Algorithmic verification misses context. Agentic verification hallucinates. Together, they catch what each misses." Solve closes the loop with a remediation agent whose fixes are re-verified before they merge. The cited numbers: a 44% reduction in AI-derived production outages among disciplined organizations, up to 92% fewer AI-induced issues at large financial institutions, a project timeline from 10 days to 4 — by generating fewer things that needed fixing.

The pattern is independently confirmed by Fowler's retreat notes: "Code generation is no longer the bottleneck — verification is," with the three-day investigation of an agent-inserted feature nobody asked for as the microcosm — "the agent saved someone 30 minutes of typing and cost the team three days of investigation." Fowler's sharper observation: agents don't learn. "Every mistake an agent makes, it will make again unless the harness explicitly prevents it." The DSL idea in the same post is verification by construction — a restricted interface where the wrong thing is unexpressible, pledge(2) for agents. And the mob programming post supplies the failure the pattern exists to fix: LeadDev's analysis of 25,264 agent-generated PRs found 79% were reviewed by the same developer who prompted the agent. The self-review problem is why the verifier must be a separate layer, not a habit. The DeepSeek teardown adds the framing from the composability paper's reflection: "composition makes change safe; verification makes change right."

The tradeoff. Verification is the new bottleneck, which means it is the new cost center: every layer of checking is tokens, latency, and infrastructure, and the checks that caught nothing still had to run. The agentic verifier layer is itself an LLM — it hallucinates — which is why the pattern insists on multi-layer verification and why the agentic layer must be validated against the algorithmic layer it complements. Over-verification is a real failure mode: the harness that reviews every token spends its budget proving the obvious and misses the consequential. And verification infrastructure, like the harness that hosts it, can rot: checks that never fail stop being checks, which is why the best harnesses turn incidents into permanent cases (Pattern 11) and why the strongest teams prove their checks can fail (Pattern 13).

Pattern 11 — The Harness Is the Instrument: data-driven design

The data-driven design post opens with the database analogy: query optimization used to be folk expertise — "always index foreign keys" — until teams started treating performance as a measurement problem, and the same transition is now happening for agents. "The defining quality of an LLM is that it is stochastic. The only way to reason about a stochastic system at scale is with data." The method: instrument every decision (tool choice, diff compiles, tests pass, loop converges), define success numerically rather than narratively, compare at scale ("a single run is a data point; a thousand runs is a distribution"), and close the loop — deploy, observe, compare, improve, deploy again. The reason the harness is the most under-invested part of an agent system is that it is the measurement instrument: "a harness that can only tell you 'pass' or 'fail' is a thermometer with one marking."

The harness engineering canonical post is the practical half: capture full inputs, tool calls, and outputs; replay deterministically; isolate external dependencies; score with explicit checks instead of vibes; and prefer layered checks — prompt-level, tool-selection, state-transition, final-outcome — so failures stay legible ("the planner chose the wrong tool" instead of "the agent failed"). The highest-value cases come from production misses, and "the best harnesses turn yesterday's incident into tomorrow's baseline." The taxonomy from the task-harness material that fed the canonical post distinguishes the three instruments: eval harnesses for fast filtering (deterministic, high throughput, reproducible aggregates), task harnesses for realistic end-to-end work (stateful, non-deterministic, messy), and agent harnesses for integration and safety (sandboxing, step-level instrumentation) — use them together, evaluate cheaply, validate realistically, instrument deeply.

The tradeoff. Instrumentation is infrastructure: it costs engineers, compute, and time before it produces anything, and the teams that need it most are the ones least willing to pay. Sample size is unforgiving — a 2% improvement on 10 tasks is noise, and the harness must support the volume that separates signal from noise, which is expensive for realistic tasks. The measurement asymmetry documented in the token post applies here too: agent spend is measured to the token while agent productivity is not measured at all, so in the absence of instrumentation "the accounting department will set the pace." And there is a subtler trap: the instrument shapes the agent. A harness that only measures final outcomes teaches the team nothing about step 2; a harness that measures everything drowns the signal. The layering is the discipline, and the discipline is the cost.

Pattern 12 — Tasks That Fight Back: the curriculum

A harness should ask for tasks that are "small enough to score, rich enough to require multiple steps, messy enough that shortcuts stop working. If every test can be passed by pattern-matching the prompt, you are not measuring the assistant — you are measuring prompt luck." That is the tasks-that-fight-back principle from the harness canon: real repos over toy snippets, failing tests over vague grading, issue-driven tasks over isolated prompts, real browsers over polite demos, the whole operating system when the agent claims the desktop. The resistance is the teacher — "a task that does not resist teaches the agent that resistance does not exist."

The pattern escalates into the curriculum once the loop closes. The distillation post is the sharpest statement: a 350M-parameter model fine-tuned for a single epoch on 187,542 tool-calling examples reached 77.55% on ToolBench against ChatGPT-CoT's 26% — "the future is not one omniscient model. It's a swarm of tiny specialists... The large model trains them. The small models do the work. The loop is the product." The closed loop is the moat: the model generates its own training data from its successful trajectories, and each round compresses the failure modes into the distribution. The DeepSeek teardown shows the harness side: the minimal preset — two tools (a persistent shell plus str_replace_editor) and a one-sentence system prompt — "owns the complete Claude SWE-compatible RL agent composition," which is to say the training environment is shipped unchanged as a product option, and "the harness produces the trajectories; the trajectories feed post-training; the trained model goes back to work inside the same harness." The benchmark evidence that the harness is the curriculum: terminal-bench-rl reports harness-level improvements — native tool calling, execution optimization — lifted scores without training, and Meta-Harness reached 76.4% on Terminal-Bench 2.0 and "was itself discovered through automated harness evolution."

The tradeoff. Hard-to-game tasks are hard to score: the messier the task, the more judgment the grading requires, and the more the verifier (Pattern 10) becomes the weak link. Realistic infrastructure is expensive — repos, browsers, OS-level observation, sandboxes — and the cost multiplies with the sample sizes Pattern 11 demands. And the loop cuts both ways: "the loop optimizes whoever runs it." A harness that rewards shortcuts breeds shortcut-takers; a harness that measures the wrong outcome bakes the wrong behavior into the curriculum and, through the closed loop, into the model itself. The tasks are not only an evaluation — they are the training data, which is the strongest argument for getting them right and the strongest warning against letting them drift.

Pattern 13 — The Harness Builds the Harness

The deepest pattern in the DeepSeek archive is process as product. The repository's AGENTS.md is a standing-order document for agents; decisions live in Agent Notes that must ship in the same PR as the decision, each with an "alternatives considered" section — "a decision recorded without what it beat invites re-litigation"; generated catalogs are freshness-gated by verify-* generators that fail on drift; keyless snapshot tests replay a recorded session log against expected output; per-file 100% coverage is the CI gate; and the self-referential toolset (cordis_inspect, cordis_mount, cordis_unmount) lets the agent inspect, mount, and unmount plugins in its own live runtime, with unmount waiting for every owned effect to reach quiescence. The outcome numbers: 683 English design records, 12,293 commits in 64 days, more Markdown files than TypeScript files, 27 pre-release checks added one incident at a time.

The loop engineering post frames the same pattern at the level of the human: Peter Steinberger's "you should be designing loops that prompt your agents," Boris Cherny's report that 100% of Claude Code's contributions in thirty days — 259 merged PRs — were written by loops he designed, Addy Osmani naming it loop engineering. The post's historical claim is that this is not new — "The need for feedback was stressed many times" is on page 11 of the 1968 NATO report that named software engineering, and Perlis's "the simulation becomes the system" is TDD and loop engineering in one sentence. The self-improving workflow material consolidated into the harness canon adds the minimal loop: read lessons → do work → reflect → write lessons, with usage data deciding which harness cases matter.

The tradeoff. Self-improvement needs enforcement, or it degenerates into self-delusion: notes as PR gates, drift-failing generators, postmortems that do not count until their check is proven to turn red — each is a mechanism against the pattern's own failure mode. The self-referential toolset is the honest statement of the risk: "the vm is an API narrowing, not a security boundary," and the composability paper's caveat applies — recovery guarantees clean removal, but removal still has to be invoked, and the interesting failure is the one where a faulty self-modification disables the very process needed to recover. The process numbers cut both ways: "this process is bureaucracy in a human team; in an agent team, it is guardrails, because the writer never gets tired" — but the same enforcement that makes an agent team productive can become ceremony when the humans are the bottleneck. And the loop optimizes whoever runs it: the harness that builds the harness is building the thing that will eventually not need the builder.

How the patterns compose — and where they conflict

The catalog is not a menu; the patterns interact, and some of the interactions are contradictions that have to be managed explicitly.

Patterns 1 and 2 both want the same log, differently. The append-only log is an audit trail and a replay source; durable execution needs checkpoints and exactly-once resumption. They compose well — the DeepSeek replay-after-crash story is both at once — but they disagree about forgetting: Pattern 1 says never rewrite, Pattern 2's governance requirement says state must be validated, rolled back, and erased. The always-on survey's lifecycle (write → validate → organize → retrieve → act → update → forget → audit → rollback) is the reconciliation, and its finding is that the reconciliation machinery barely exists.

Patterns 1 and 3 constrain Pattern 6. The prefix-cache discipline (no clocks in the prompt, fixed ordering, append-only history) is a constraint on the interface: the agentic-first CLI's "no timestamps unless asked" is not just good UX, it is a billing requirement. Every interface change is now a cache-invalidating, bill-changing event, which is why the versioned, additive contract stops being a nicety.

Patterns 7 and 2 pull against each other. Per-agent scope wants isolation; durable-daemons choreography wants shared state as the coordination mechanism. The resolution is explicit scope discipline — which state is shared, which is scoped, who owns the boundary — the least-solved governance question in the always-on survey.

Patterns 9 and 9 disagree with themselves. Defense in depth says add layers; zero overhead says subtract them. Both are right, and the resolution is honesty about what each layer is for: the sandbox constrains the compromised agent, the small dependency graph shrinks what can be compromised, and the one-door context mediates capabilities — none of them is a wall, and the pattern is to know which one you are building.

Patterns 10 and 11 are the same budget spent twice. Verification costs tokens and latency; instrumentation costs infrastructure and sample size. The token post's arithmetic — the bill is 2-14% of labor cost — is the budget that both have to fit in, and the teams that win are the ones that make verification output be the measurement data: layered checks that fail legibly are both the gate (Pattern 10) and the instrument (Pattern 11).

The meta-pattern across all of them is the one the DeepSeek teardown's two independent analyses converged on: the harness is the product. The same model swinging from 47% to 67% across eight harnesses, the same weights 3.4 points apart under two harnesses on the public board, harness-level improvements lifting scores without any training — the wrapper is where the leverage is, which is why the wrapper deserves a pattern catalog at all.

What to steal regardless

The catalog is drawn from this blog's own archive, and the posts it distills each end with the same kind of list. The portable items, independent of any particular stack: the session log as single source of truth with a logged-surface invariant (Pattern 1); checkpointed, replayable state with idempotency keys at the boundary (Pattern 2); the bill as a CI assertion — one test that fails when the prefix breaks (Pattern 3); the loop as a replaceable component with reversible effects (Pattern 4); definition/provider/consumer seams only where roles evolve independently (Pattern 5); the agentic-first contract on the interfaces you already ship (Pattern 6); per-agent scope and portable identity as separate axes (Pattern 7); waterfalls for extensible policy, monotonic guards for final denial, fail-closed approval (Pattern 8); a sandbox stack whose layers assume each other's failure, with honest scope declarations (Pattern 9); verification as a separate, multi-layered function, not a habit (Pattern 10); instrumentation and numeric success criteria as the only reliable design method for stochastic systems (Pattern 11); tasks that fight back, because the tasks are the curriculum (Pattern 12); and recorded decisions with enforced alternatives-considered, because the harness that builds the harness is the one that improves (Pattern 13).

The tradeoffs are not defects in the patterns; they are the prices. Every harness pattern in this catalog buys a guarantee and charges a cost, and the honest harness engineer is the one who can state both for each layer of the stack. The guarantee stops where the declaration stops — file effects only, bash-equivalent trust, observational equivalence, within the control boundary. Name the boundary, design within it, and verify the design works. That is the engineering method, and it is the whole catalog in one sentence.
