On August 13, 2026, DeepSeek AI opened a repository called [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) — `dsh`, an open-source agent harness in TypeScript, MIT-licensed, whose one-line description is the whole design: **"Everything is a Plugin."** Four days later it had more than 149,000 GitHub stars — the count was passing 150,000 as this post was written. That is an extraordinary reaction to any repository, and it is even more extraordinary for one that is explicitly a developer preview promising compatibility-breaking changes, with no external plugin ecosystem yet and no tagged stable release (the shipped artifact is `0.1.0-rc.7`).

This blog covered the intellectual foundation of that repository two days before it existed as a GitHub URL. On August 13 the same day the repo appeared, an 88-page paper was published from the [cordiverse/paper](https://github.com/cordiverse/paper) repository: *A Programming Paradigm for Spatiotemporal Composability*, by Yifan Shi and Wei Zhang of Peking University and Tianyi Cui of DeepSeek-AI. I summarized and reflected on it in [Spatiotemporal Composability: The Missing Calculus for Self-Evolving Agents](https://blog.hackspree.com/#spatiotemporal-composability). The paper formalizes *dynamic* composition — components loaded, unloaded, and reconfigured at runtime — with two guarantees: **temporal composability** (when a component is removed, everything it did is undone) and **spatial composability** (when the world changes, components whose dependencies changed reconnect or wait, never crash). Its authors extracted the theory from Cordis and Koishi, a plugin framework and a chatbot framework with 4,000+ community plugins.

DeepSeek Harness's README says in its second line: it is "powered by [Cordis](https://github.com/cordiverse/cordis), whose design is described in *A Programming Paradigm for Spatiotemporal Composability*." The calculus this blog called "the missing calculus for self-evolving agents" is not a proposal anymore. It is the runtime under DeepSeek's own agent harness. This post reads the documentation site — [deepseek-harness.github.io/deepseek-harness/en/](https://deepseek-harness.github.io/deepseek-harness/en/) — the way the project's own docs ask a reader to read it, and then reflects on what the design actually buys and where its guarantees stop.

## The documentation is part of the design

The English docs live at a VitePress site that mirrors a bilingual source tree in the repository — every page is projected from Markdown in `docs/`, with a Chinese counterpart kept in sync by a custom Git merge driver. The landing page is a one-line redirect to **Guide → Use the Web UI**, which is the honest shape of the project: the fastest path is `npx @deepseek-ai/dsh web`, which serves a web UI at `http://127.0.0.1:3080`, where you add a DeepSeek API key, choose a workspace, and send the agent a task.

Three nav sections matter more than their titles suggest. **Guide** is user-facing (Web UI, model configuration, a Python SDK). **Development** is plugin authoring, including a seven-part Cordis tutorial. **Reference** is the interesting part: an architecture page, a Cordis primer, capability seams, the agent lifecycle, the tool execution pipeline, then a long list of **subsystem pages** — one per capability (sessions, tools, shell, sandbox, approval, compaction, skills, subagents, workflows, and more) — each ending in a *generated* Cordis API section with the exact service methods and event signatures, byte-identical to the source, freshness-checked by a build gate so a JSDoc edit cannot ship without regenerating the catalog. The docs also include generated catalogs of every plugin config field, every model-facing tool schema, and every durable session event.

This is not documentation hygiene trivia; it is a design decision worth naming early. The repository treats its documentation as a machine-checked artifact: type declarations pasted into docs are verified drift-free against source (`verify-type-equiv`), generated catalogs must be byte-fresh (`verify-cordis-catalog`), and the `AGENTS.md` documentation standard enforces word budgets per document tier. The reason is stated plainly in the architecture page: "We recommend using an agent to explore the codebase." The documentation is written to be read by agents — which is exactly what a harness company's documentation should be, and almost none of it is.

## The architecture: one running harness, every row a plugin

The architecture page makes the first move the README's tagline implies, and then goes further than any "plugin system" claim usually does:

> There is no privileged core to patch: you extend dsh by mounting a plugin beside the others, and registrations are effects that unwind when their plugin unloads.

The composition mechanism is worth understanding precisely, because it is the product. A running `dsh` is a **plugin tree** composed at boot from ordered layers. A **profile** is a named composition stored in the Harness home — `web` and `headless` ship as templates. A **bundle** is a distribution format: config rows plus the code they mount. `dsh-base` is the first layer of every profile (model adapters, tools, persistence, sandbox and approval policy, settings, credentials, telemetry); `dsh-web-app` adds the browser application; `dsh-headless` adds a one-shot runner with no server at all. Layers apply to an empty entry list in order: each bundle in the profile's listed order, then the profile's `cordis.patch.yml`, then the home-level one, then any `--patch` overlay. A **patch targets a row by id and replaces its whole config, or inserts new rows.**

The command that makes the design legible: `dsh --profile web --dump-config` prints the tree your machine actually boots, and the docs' claim is total — "any row it prints can be replaced by a patch of your own." The model adapter, the tool registry, the session log, the agent loop itself, the sandbox, the approval policy: all rows in a tree, all replaceable from configuration.

![One running harness — a profile stacks bundles (dsh-base, dsh-web-app, dsh-headless), patches replace rows, and the composed tree exposes every service as a ctx key. dump-config prints the tree; any row it prints can be replaced.](/images/dsh-composition-tree.png)

The core packages map to a stable set of context keys — `ctx.sessions` (the session log), `ctx.systemPrompt` (prompt assembly), `ctx.tools` (the tool registry and guarded execution pipeline), `ctx.agents` (the live agent registry), `ctx.agentLoop` (the default driver), `ctx.llm` (the model adapter seam), plus a `ctx.scope` library primitive for per-agent registration. The correspondence between "package" and "context key" is the harness's public interface: a plugin finds a service by key instead of importing a concrete implementation.

The Cordis primer distills the framework beneath this into five ideas: a plugin is an object that implements Service; a context is a repository of services; service dependencies are declared via `inject` so load order is expressed as requirements, not boot sequencing; services communicate through typed events dispatched as `emit`, `waterfall`, `parallel`, or `serial`; and **registrations are reversible effects** — prompt sections, tool schemas, adapters, providers, and listeners are installed through `ctx.effect()` or `ctx.on()` so reload and teardown unwind them predictably. The waterfall semantics deserve emphasis because they are the policy engine: a listener receives `(...args, next)`; call `next()` to delegate, return without it to short-circuit. For single-decision events, short-circuiting *is* the design — a policy listener that owns the decision returns without `next()`, while a listener that only annotates must delegate.

## The session log is the source of truth

The subsystem that makes everything else coherent is the **session log**. A session is an append-only log of typed `SessionEvent`s — the single source of truth for an agent's whole interaction history. The LLM message history is *derived* from the log, never stored separately; replay is re-derivation from the same events.

The invariant that follows is stated twice in the docs, once as a rule and once as a runtime check: **model-visible means logged.** Anything that reaches a model request must be reconstructable from the log, and a runtime invariant asserts it. Raw `assistant/chunk` events are preserved for token-level replay fidelity; fork, resume, transcripts, telemetry, and persistence all derive from the same stream. A plugin that wants to add model-visible input must add a session event type and render it from the log — there is no side channel into the prompt.

The lifecycle vocabulary sits on top of the log. A **step** is one model request plus the tools it calls; a **turn** is zero or more steps, opened before its first input is claimed and closed once nothing is owed. The turn flow is a documented waterfall chain: `turn/start` → claim input → `agent/pre-step` (listeners may rewrite or reject the messages the model will see) → `step/start` → `user/message` → `agent/request` → `llm/stream` → `assistant/chunk*` → `assistant/message` → `tool/call*` through the tool pipeline → `step/end` → repeat while tools owe another request → `agent/turn-stopping` → `turn/end`. Durable facts live on `session/event`; live control and status live on `agent/*`. The two-plane split is the project's answer to the replay/streaming tension: a UI or SDK renders from the durable stream, coordinates through the live API.

## Capability seams: the swap is the product

The architecture's middle layer is the **capability seam**: a swappable capability with three roles — a **Service Definition** declaring the interface, a **Service Provider** implementing it, and a **Consumer** using it, commonly a model-facing tool. One role alone is not a seam; adding a capability means designing all three.

The payoff sentence is on the architecture page: "Seams are why one provider swap changes the whole product." Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks. The subagent seam makes the point even more sharply — providers registered by name (`ctx.subagents`) include in-process spawn, fork, ACP, Codex, Claude Code, and the dsh SDK itself, all behind one interface, from "a fresh child agent" to "a delegated turn in another product." A subagent provider advertises its start-time capabilities statically — output schema, depth limit, tool filtering, persona — and a request needing a capability the provider lacks is rejected loud before any run exists, never accepted-then-ignored.

## The tool pipeline: policy runs in waterfalls

Every tool call passes through a pipeline the docs render as a flowchart, and the layout is the message: the loop never changes; policy attaches at documented points.

The call is logged as `tool/call` before execution — the durable record precedes the action. Then `tools/pre-execute` runs as a waterfall: hooks, permission, sandbox decisions. Registered **monotonic guards** run next — they deny or abstain, and their identity is protected, meaning owner policy that must not be reordered stays a guard rather than a waterfall listener. If approval is needed, `ctx.approval` resolves a one-shot question before the guards continue; a missing, non-owning, throwing, or non-conforming answerer resolves to `unavailable`, and callers fail closed unless the outcome is `allowed-once`. Then `tools/execute` wraps the registered tool body as an around-dispatch (timeouts, retries, metrics), `tools/post-execute` may accept, block, replace, or add context, and a definition-owned `finalizeContent` callback enforces the last content-only invariant — it must be total and must not throw. Finally `tools/result` observes the frozen, lossless-JSON outcome, and `tool/result` lands in the session log as the single model-facing result.

![The tool execution pipeline — model → tool/call → pre-execute waterfall → monotonic guards → approval → execute → post-execute → frozen result. Policy attaches at documented points; the loop does not change.](/images/dsh-tool-pipeline.png)

The design discipline shows in the details: tool schemas assembled for the model are allowlisted (output declarations, timeouts, and concurrency metadata never leak into a model request); timeout budgets are cooperative, asserting the tool forwards the execution signal; parallel tool calls are opt-in and require the tool to tolerate concurrent dispatch or fail closed; the final outcome is frozen before observation so hooks cannot see different results than the log records.

## Enforcement: sandbox modes, permission presets, fail-closed approval

The sandbox is deliberately scoped and the docs are explicit about the scope. `SandboxMode` governs **filesystem effects only**: `read-only` (deny writes, granting only required sinks like `/dev/null`), `workspace-write` (permit writes under the workspace root and a backend-defined temp area), and `danger-full-access` (bypass confinement entirely). Network and process visibility are explicitly outside this vocabulary. Backends are Linux bwrap/Landlock, macOS Seatbelt, and a Windows ACL restricted-token runner, and enforcement is reported as a fact: `full` or `partial` — older Landlock ABIs and the Windows ACL runner's Everyone/hard-link boundaries are current partial cases, and consumers that require the absolute promise must reject or surface that distinction.

The policy is resolved **per call**, not fixed on the provider: bash under `read-only` while a confined child agent needs its state directory writable, and an approved escalated retry is a new call with a wider policy. Two independent knobs — sandbox mode and approval policy — are bundled into named **permission presets** a client offers as a single Permissions selector; the default table ships `workspace-write` (workspace-write + ask) and `danger-full-access` (danger-full-access + never). The `never` approval policy is described with unusual honesty: "the strict headless stance (CI, unattended runs) and the policy whose outcome is knowable without asking."

The **defensive patterns** page deserves mention as the most transferable document in the tree. It records bug classes that "actually shipped or nearly shipped here," each stated as the rule that prevents recurrence: report orthogonal outcomes independently (a process can time out AND exit 0 because it trapped the signal); honor public contracts on both sides (normalize every provider failure form into one terminal finish before it crosses the public API); async state is not synchronous state (`whenIdle()` is not the result of one follow-up); dispose must reach quiescence, not just request it; contain callback exceptions in the dispatcher so one bad subscriber never breaks core lifecycle; never hand untrusted output the ambient environment or predictable paths — spawned commands get a scrubbed env (any `*KEY*`/`*SECRET*`/`*TOKEN*`/`*PASSWORD*` variable dropped) and temp files use a private 0700 directory with random names and exclusive owner-only opens; unlink link-shaped paths without following them. These are the bug classes every harness team will eventually pay to learn; the docs sell them for free.

## The self-referential toolset

The part of the docs that connects most directly to this blog's [prior coverage of the spatiotemporal calculus](https://blog.hackspree.com/#spatiotemporal-composability) is a small, opt-in extension: `@deepseek-ai/dsh-tool-cordis`, demoed by `pnpm run demo:cordis` — which the repository README describes in four words: "the agent modifies its own runtime."

The agent gets three tools over the live Cordis runtime in its own process. `cordis_inspect` reports the live runtime — every plugin fiber, every provided service, the model-visible tool set, and, on demand, exact service signatures and event declarations with their original JSDoc, served from a generated API catalog kept fresh by a build gate (so the agent reads the same contracts the docs print). `cordis_mount` evaluates a model-written async JavaScript body in a `node:vm` sandbox and mounts the result as a **temporary Plugin** — it can register tools, listen to events, provide services, inject dependencies, in the shared runtime. `cordis_unmount` unmounts one temporary plugin by id and returns only after every owned tool, listener, service, timer, and effect reaches quiescence.

![The self-referential toolset — the agent inspects, mounts, and unmounts plugins against its own live runtime. Reversible effects make unmount wait for quiescence; the vm narrows the API but is explicitly not a security boundary.](/images/dsh-self-referential.png)

The design notes are as honest as the sandbox ones. Temporary plugins exist only in process memory — they create no file, install no package, change no `cordis.yml`, do not survive restart, and are never restored automatically; keeping an experiment means asking the agent to implement a normal project plugin. Cross-mount composition works through ordinary Cordis semantics: mount A calls `ctx.provide('foo', value)`, mount B declares `inject: ['foo']` and activates the moment `foo` exists; unmounting A sends B back to pending, its registrations unwound. And the posture is stated in plain terms: the vm sandbox and the context façade **narrow the API** mount code sees — steering it onto Cordis services and away from leak-prone Node built-ins — but the capabilities the façade exposes reach the real runtime. "This is an opt-in development tool with bash-equivalent trust, not a security boundary or product default."

That posture matters, because it is the correct reading of what the spatiotemporal calculus provides. The calculus guarantees *clean removal*: unload a plugin and its effects unwind, dependents reconnect or wait, no restart, no orphaned listeners. It does not guarantee *harmlessness while present*. A mounted plugin that runs `ctx.shell` with the host executor's privileges can do whatever shell can do — the reversible-effect machinery makes it *removable*, not *safe*. The blog's earlier reflection on the paper made the same point: the one-door context is a policy chokepoint, but capability mediation is not a code sandbox. DeepSeek Harness draws the line in the same place.

## A harness built to be built by agents

The development guide is worth a paragraph because it is the strongest evidence about who this project is for. The repository's `AGENTS.md` is a standing-order document for agents: every npm package is `@deepseek-ai/dsh-*`; registrations are effects; runtime invariants assert owned relationships, never service presence; waterfall listeners must call `next()`; model-visible ⟺ logged; misconfiguration fails loud; decisions live in **Agent Notes** — decision records under `.agents/notes/` that must ship in the same PR as the decision, archived when superseded. The repo layout includes a `self-modification/` package group and a `hooks/` group implementing the Claude Code and Codex hook wire protocols — the harness can bridge to other coding agents as subagents and expose its own extension points to them as hooks.

The testing policy is harness-shaped in the same way: per-file 100% coverage as the CI gate; **keyless snapshot tests** that replay a recorded session log against expected model output so behavior is verified without spending tokens or flakiness; real-API e2e suites that self-skip when `DEEPSEEK_API_KEY` is absent. The session log that is the product's source of truth is also the test fixture format. The translation-pairing merge driver, the worktree-local Lefthook hooks, the `verify-*` gates on generated catalogs — every process detail says the same thing: this repository was built by and for agents, with the harness's own invariants (reversible effects, logged surfaces, fail-closed policy) applied to its own development.

## Reflecting: what the design buys, where it stops

**The bet.** Building the whole product on a plugin framework with reversible effects is a wager that harness engineering is, at bottom, a dynamic-composition problem: the hard parts of an agent runtime — adding capabilities, swapping providers, reloading policy, cleaning up after a failed experiment — are the hard parts of runtime plugin management. The wager is coherent, and the evidence base is not trivial: the framework underneath shipped in Koishi with 4,000+ community plugins before the theory was written down. The paper's own conclusion is the honest version of the story: the theory was extracted from a working system, not written first and applied later. What the formalization buys is the second product — dsh did not have to re-solve plugin lifecycle, HMR, dependency resolution, or teardown; it inherited them as a vendored, formalized substrate and spent its own complexity budget on agent concerns: the session log, the seams, the pipeline, the policy. That is exactly the economics this blog keeps returning to in [harness-engineering-best-practices-for-ai-agents](https://blog.hackspree.com/#harness-engineering-best-practices-for-ai-agents) and [go-is-good-for-harness-pipelines](https://blog.hackspree.com/#go-is-good-for-harness-pipelines): the harness is where composition complexity concentrates, and the team that treats composition as the product wins the cost curve.

**The guarantees stop where the paper's do.** Observational equivalence, not literal restoration — unplugging a component does not restore the heap's exact layout, only what the declared dependencies observe. The sandbox vocabulary covers file effects only; network and process visibility are out of scope by declaration. The self-modification toolset is bash-equivalent trust, explicitly not a security boundary. And the deeper caveat survives from the paper: recovery guarantees *clean removal*, and for agents the interesting failure is the one where a faulty self-modification disables the very process needed to recover — the calculus makes removal safe, but removal still has to be *invoked*.

**The preview caveat.** More than 149,000 stars in four days is a demand signal, not a validation of production readiness. The README's first declaration is "developer preview... THERE WILL BE COMPATIBILITY-BREAKING CHANGES." The session log carries `SESSION_FORMAT_VERSION` at 0 with no compatibility promise; backends reject old on-disk formats. The release cadence is remarkable — `0.1.0-rc.7` and 2,600+ merged PRs by day four — but that velocity is exactly the argument for treating the docs as the product's present shape and the code as a moving target. The single-process runtime is another boundary worth naming: everything runs in one shared process, so the compositional guarantees are process-internal; cross-process isolation is delegated to the sandbox providers and the subagent seams, which is where the real blast-radius questions live.

**What to steal regardless.** The session log as single source of truth with a *logged-surface invariant*; the seam discipline (definition / provider / consumer, one role is not a capability); the tool pipeline as a waterfall of policy with monotonic guards for final denial; the docs-as-machine-checked-artifact practice with freshness-gated generated catalogs; the defensive-patterns page as a bug-class ledger; the honest scope declarations (file effects only, bash-equivalent trust, per-call policy). Any harness team can adopt any one of these without adopting Cordis. The project's most distinctive move — and the reason this blog's earlier [spatiotemporal-composability](https://blog.hackspree.com/#spatiotemporal-composability) coverage connects to it directly — is that it makes the plugin runtime itself the product surface: `dump-config` prints your machine's tree, any row is replaceable by a patch, and the agent that runs inside the tree can inspect, mount, and unmount its own components. Four days after the calculus appeared on arXiv-style GitHub, it was the shipping substrate of a ~150,000-star harness. The theory mattered; the harness is what the community voted for.
