Spatiotemporal Composability: The Missing Calculus for Self-Evolving Agents

A new 88-page paper from Peking University and DeepSeek-AI — A Programming Paradigm for Spatiotemporal Composability — gives dynamic composition its first formal foundation: revertible effects, where removing a component completely reverses its side effects, and reactive coeffects, where dependencies rewire themselves as providers appear, disappear, or change identity. It is the theory behind Cordis, the framework powering Koishi's 4,000-plugin ecosystem, and it is the missing piece for the one thing agent harnesses are about to do: modify themselves at runtime. Here is why this paper matters for agentic design.

On August 13, 2026, an 88-page paper appeared on GitHub: A Programming Paradigm for Spatiotemporal Composability, by Yifan Shi and Wei Zhang of Peking University and Tianyi Cui of DeepSeek-AI, published from the cordiverse repository. Within two days it had over 1,500 GitHub stars — an unusual reaction to a paper whose tools are monads, coeffects, and operational semantics.

The reaction is deserved, and it is not about the mathematics. The paper is the first formal foundation for a problem every agent engineer is about to hit head-on: software that modifies itself at runtime. Plugin systems do this today, badly. Agent harnesses will do it next — an agent generating, installing, replacing, and removing components of its own runtime while continuously serving requests. The paper gives that act a theory: two guarantees, called temporal and spatial composability, plus a calculus that carries them from a single component to a whole system, plus a working implementation with a four-year, 4,000-plugin production track record.

Agents are about to modify their own harness. Today there is no theory for doing that safely. This paper is the theory — and it has already been proven in production.

The problem nobody formalized

Composition — assembling complex systems from simpler parts — is the most-studied topic in software engineering, opening, as the paper does, with Parnas's 1972 modularity criteria. But the study has been almost entirely about static composition: function calls, module imports, class inheritance, all resolved at compile time and fixed for the life of the process. Static composition has a rich formal apparatus: type systems, module systems, category theory, algebraic effects.

Dynamic composition — components loaded, unloaded, and reconfigured at runtime — has almost none. The paper's motivating example is measured, not anecdotal. In Visual Studio Code, all extensions run in a shared extension host with no mechanism to unload a single extension's code at runtime. Among the top 100 extensions by install count, 87 contain executable code and therefore require a host restart to remove. The deactivate hook is a graceful-shutdown callback for process termination, not a live-removal mechanism — and it separates effect disposal from effect creation, violating locality of concern and making complete cleanup impossible to verify. On the other axis, only 7 of the top 100 extensions declare extensionDependencies on non-built-in extensions, and the one mechanism for inter-extension interaction returns an untyped any. VSCode doesn't fail at dynamic composition; it steers around it.

Why does practice punt? Because operating systems and container orchestrators provide a coarse-grained workaround: restart a process to get rid of a misbehaving module, let the orchestrator manage service dependencies. The paper's cost accounting for this workaround is the quiet heart of the motivation. Temporally, every restart discards all process-local state — caches, connections, partial computations — and rebuilding it takes seconds to minutes, with redundant replicas bought to cover the gap. Spatially, container-level orchestration cannot express dependencies between components sharing an address space, and turns local function calls into network calls. Modern systems increasingly compose at a finer grain than processes and containers; the workaround is a granularity mismatch, and it is the only mechanism anyone has.

Two dimensions of composability

The paper's central move is to name the two requirements of dynamic composition as orthogonal dimensions, each with a familiar static degenerate case:

  • Temporal composability — when a component is removed, the modifications it made to the shared environment must be completely and safely reversed: every resource allocation, event registration, and state mutation, reclaimed in order. In the static setting this reduces to lexical scoping — RAII, bracket patterns. In the dynamic setting the effects are long-lived and stateful, with no lexical scope to bound them.
  • Spatial composability — components must declare, discover, and resolve their dependencies on one another in a structured and verifiable way, and their lifecycles must coordinate as dependencies appear, disappear, or change identity. In the static setting this reduces to module import resolution. In the dynamic setting a dependency can vanish mid-execution.

These two dimensions map one-to-one onto the two ways self-modification can kill an agent harness. The paper spells out the temporal failure: "a faulty self-modification can disable the very process needed to recover." And the spatial failure: "a naive code-replacement strategy may silently break dependents or introduce circular dependencies that surface only at reload time." Note what the second sentence says: the failure is invisible until the next reload — the exact moment the system needs to keep working.

Revertible effects, reactive coeffects

The paper's constructive idea is to lift two classical, compile-time concepts to runtime mechanisms — and this is where it stops being a position paper.

Revertible effects. An effect system tells you at compile time what a computation may do. Here, every context transformation carries an explicit inverse that the runtime tracks, and both tracking and recovery preserve composition: the inverse of a composite effect is the composition of the inverses, automatically. A component's teardown is therefore derived from its loading rather than written alongside it. The developer supplies the inverse of each atomic operation once; the runtime composes them into ordered cleanup on removal. This is what makes uninstallation a structural property instead of a discipline.

Reactive coeffects. A coeffect system tells you what a computation requires of its environment. Here, a component declares its required dependencies as a specification, and every change of the context notifies the component against that specification, classifying each change as activating, deactivating, or neutral. A component whose dependency is missing stays inactive — it does not error — and becomes active the moment the dependency appears. Two refinements carry the security weight: isolation varies what a declared key resolves to (what a dependency request means), and interception varies how the binding is used (what calls to it are permitted).

The two mechanisms are then unified into a single context type, written Γ∞ ≔ μΓ. Γ × (Γ → Γ) × Σ: the current state, the accumulator that recovers this level's effects, and the coeffect context carrying dependency information — recursive, so a parent context aggregates its children's effects and any state the system shares can be encoded as a dependency. Every interaction between a component and its environment passes through this one entity. The paper's metaphor is literal: loading a component executes its effects (plugging in); unloading recovers them (unplugging) without affecting other running components; components at different hierarchy levels are independently loadable, enabling arbitrarily nested composition.

The context paradigm

The paper argues the unification is a programming paradigm in its own right, positioned between the two poles of side-effect handling:

  • Functional: state threaded explicitly through every call. Traceable, equational, and — as the paper notes — full of boilerplate; each new effect dimension (logging, config, I/O) adds a monadic stack or handler.
  • Imperative/OOP: implicit mutation. Ergonomic, and untraceable: React's useEffect registers a persistent side effect whose target and registration mechanism appear in no parameter; Spring's getBean(...) pulls dependencies from a process-wide registry with null-checks and casts at every call site. Understanding how a call modifies or depends on the system means reading its implementation transitively, and refactoring silently breaks distant invariants.
  • The context paradigm: effects and coeffects mediated through an explicit context parameter. Each operation is attributable to the context it ran on, and hence to the component that context belongs to — the traceability of the functional approach with the ergonomics of the imperative one.

The claim that matters: "correctness that would otherwise rest on developer discipline becomes a structural property of the paradigm." For human-written plugin authors that is a quality-of-life improvement. For autonomous agents — whose "discipline" is a prompt, and whose mistakes are generated at machine speed — it is the difference between a harness that can evolve and a harness that self-destructs.

The metatheory

The paper does not stop at mechanisms. It defines a calculus of dynamic composition — components as fibers with an operational semantics for their full lifecycle: loading, iteration, withdrawal, asynchrony, failure — and proves the properties that matter: preservation, temporal composability, spatial composability, progress, and confluence. The point of the metatheory is explicitly compositional: it carries the two guarantees from a single component to a whole system of interleaved components. Local reversibility and local reactivity compose into system-level guarantees — which is precisely the property a self-modifying system needs before anyone should let it modify itself unattended.

One honest idealization, which the paper states plainly: recovery is guaranteed up to observational equivalence, not up to literal state equality. Unloading a component does not restore the heap to its exact prior layout — free releases a block without restoring the layout malloc left; a generative name is not undone by discarding it. What the runtime guarantees is that no observer can tell the difference, where what counts as an observer is fixed by the coeffects: the state that is observable, declared, and bound is the state that is recovered. This is the right definition, and it is also the one caveat to carry into any deployment: the guarantee is about observable state, so what you choose to expose as dependencies defines the boundary of what recovery can promise.

The proof it works: Koishi

The paper's theory was not written first and applied later. It was extracted from a working system. Koishi, an open-source chatbot framework built on Cordis, has accumulated over 4,000 community-contributed plugins over four years — IM adapters, database drivers, admin consoles, end-user features. Three results stand out.

Temporal composability without cognitive overhead. An orchestrator disables a plugin from the console and its effects are withdrawn in place; during development, hot module replacement re-applies edited plugins on save while preserving cache state and live connections elsewhere. Because effects performed through the context are tracked and their inverses composed automatically, even an inexperienced plugin author gets ordered cleanup without writing an uninstall path. Correctness that would otherwise depend on each author's diligence is discharged once, by the abstraction.

Spatial composability across an open ecosystem. Koishi's plugins exhibit a genuine dependency topology — adapters provide platforms, drivers provide storage — and reconfiguring a provider at runtime (switching the storage backend, reconnecting an adapter) reactivates only the dependents whose resolved dependency actually changed. A plugin whose dependency is unavailable stays inactive until it appears, without erroring. The composition holds across independently authored code: plugin and dependency are usually written by different people who coordinate on nothing beyond the coeffect that connects them.

Expressiveness and generality. Koishi's web console is a second, independent Cordis application whose plugins compose browser and UI primitives rather than server ones — the same model in a wholly different runtime. The framework contributes only domain vocabulary; the paradigm fixes how effects and coeffects compose while leaving their meaning to each application.

The paper is appropriately honest about its threats to validity: a single ecosystem, a single host language (TypeScript), observational rather than controlled evidence. What it establishes is an existence-and-adoption result — which, for a programming paradigm, is exactly the result that matters most.

Why this matters for agentic design

The paper's stated future direction is the reason to read it now: "a compelling direction for future validation is self-evolving agent harnesses, where an AI agent generates and replaces its own harness components continuously and with little human oversight." Its own citations map the field — OpenAI's Harness Engineering, Anthropic's Harness Design for Long-Running Application Development, MemGPT's agents-as-operating-systems, the multi-agent surveys. The paper is the formal foundation that this literature has been reaching for. Five reasons it is the right foundation:

  1. Self-modification is the one thing every current harness does worst. Today, an agent that "adds a tool" appends to a list; that "replaces a module" means restarting the process, dropping the warm context, the cache, the in-flight work — or worse, patching itself with hacks the harness cannot unwind. The paper's temporal guarantee is exactly the missing primitive: replace a component and have its side effects completely reversed, without a restart, without touching the components that must survive.

  2. The two guarantees are the two failure modes of self-evolving agents. The temporal failure — a faulty self-modification disabling the very process needed to recover — is the recursive-death scenario every self-modifying system eventually faces. The spatial failure — dependents silently broken, circular dependencies surfacing only at reload — is what happens the first time an agent replaces a provider other components depend on. The paper gives both failure modes a theory, which is the precondition for a mitigation.

  3. Agents cannot be trusted with discipline, so correctness must be structural. The context paradigm's central claim — teardown derived from loading, wiring derived from declarations, correctness as a structural property — is the only form of correctness that survives autonomous generation. A prompt can say "clean up after yourself"; a structure that derives the cleanup from the load cannot be forgotten. This is the same distinction this blog has drawn between agents that verify and agents that hope (Verifiers Are King, The Verification Horizon): guarantees you must remember are guarantees an agent will, at some point, not.

  4. Sandboxing falls out of the design instead of being bolted on. Because every interaction passes through the context, and dependencies are declared before a component runs, the capability set a component requires is known statically — the paper calls the declaration a "capability request" and the context proxy a "capability mediator," explicitly citing capability-based security. Undeclared access raises an error; interception carries fine-grained policy (a filesystem dependency can declare which paths a component may read or write, checked on every call, adjusted by an orchestrator without modifying either party). For agent harnesses, whose components are not merely untrusted but machine-written, access control that is structural rather than inspected is the only kind that scales (Sandboxing AI Agents, Zero Overhead Is Zero Attack Surface).

  5. The restart tax has an economics, and this blog has been counting it. The paper's seconds-to-minutes rebuild costs are the token economics of agent restarts: a restart is not a free action, it is the loss of every warm context, every cache, every connection — the exact costs this blog has measured for always-on agents and metered attention (Every Token Has a Price Tag, Always-on agents). Spatiotemporal composability is the mechanism that turns "restart to reconfigure" into "reconfigure in place" — the difference between an agent that pays the full price of state loss on every self-modification and one that pays nothing.

And the provenance matters. This is not armchair type theory: it is a paradigm extracted from a 4,000-plugin production system, with a DeepSeek-AI co-author — a frontier lab that needs harness foundations the way previous eras needed operating systems. When a paper arrives with both a formal calculus and a working meta-framework and a large production ecosystem, it is worth reading as more than theory.

The honest caveats

The paper is dense — 88 pages of monads, coeffects, operational semantics, and metatheory — and the barrier to entry is real. The guarantees come with the observational-equivalence caveat above: what is recovered is observable state, as defined by declared dependencies; the boundary between what the system can track and what it cannot (Section 6.1, the system boundary) is itself a design decision that moves as coeffects reify external locations. The implementation evidence is single-ecosystem, single-language, and not yet quantitatively measured against a baseline — overhead and developer-productivity numbers remain future work. And the paradigm is young: Γ∞ is a beautiful type, but the ecosystem that validates a paradigm is built by adoption, not by theorems.

None of these caveats change the shape of the argument. The paper has done the thing that matters most: it has named the two dimensions, given them a calculus, proven the calculus, and shipped the proof in production. Every other foundation for dynamic composition is now playing catch-up.

Bottom line

Agents will modify their own harnesses. That is not speculation; it is the stated direction of the harness-engineering literature and the paper's own future-work section. The only open question is whether self-modification is done with ad hoc patches and restarts — or with a runtime that guarantees, structurally, that a removed component leaves nothing behind and a changed dependency rewires itself safely.

A Programming Paradigm for Spatiotemporal Composability is the answer to that question: revertible effects for the temporal dimension, reactive coeffects for the spatial one, a unified context that mediates every interaction, a calculus with metatheory, and a four-year production validation with 4,000 plugins. It is the missing calculus for self-evolving agents — and it arrived, appropriately, in a GitHub repository: the first component of a future harness that is, in the most literal sense, self-composed.
